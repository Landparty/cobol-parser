# cobolparser Production-Readiness Audit — Silent Drops & Real-World IBM COBOL (2026-07-07)

Scope: `cobolparser` 1.1.0, full pipeline (preprocess → lex → parse → AST → serialization)
plus batch, CLI, and analyzers. Method: three parallel code reviews (preprocess/lexer,
parser/statements, periphery), ~30 targeted runtime probes of IBM Enterprise COBOL
constructs, a corpus sweep (459 NIST COBOL-85 files, 24 shamrice IBM examples, 54 repo
samples — 537 files), a full test-suite run, and re-verification of every open item from
`reports/audit-2026-07-06.md`. Findings marked **[verified]** were reproduced at runtime
today; **[reported]** come from code review.

## Verdict

**Not production-ready for unattended use on arbitrary real-world IBM COBOL yet — but
close, and the gap is narrow and well-defined.** The parser is crash-free (0 crashes in
537 files), fast, well-tested (6,606 tests pass, 93.4% coverage), and faithful on
mainstream constructs (aggregate statement retention across the NIST corpus is ~100%).
The blocker is a small set of **structural silent-drop channels**: constructs the parser
does not understand are discarded with `success=True, errors=0, warnings=0` instead of
being reported. Across all 537 corpus files, **`ParseResult.warnings` was populated
exactly zero times** — the warnings channel exists but the pipeline never uses it; every
drop path uses `logger.debug` instead. Until the drops below are converted into
caller-visible signals, a "clean parse" cannot be trusted to mean "complete AST".

## Empirical results

| Corpus | Files | Clean (0 errors) | With reported errors | Crashes |

| NIST COBOL-85 (`examples/cobol`) | 459 | 455 | 4 | 0 |
| shamrice IBM examples | 24 | 24 | 0 | 0 |

## CRITICAL — silent drops that corrupt real-world programs

### C1 — Multi-program compilation units: everything after the first program is dropped **[verified]**
A source member containing several programs (stacked or nested, delimited by
`END PROGRAM`) — ubiquitous in real IBM shops — keeps **only the first program**.
Minimal repro: two stacked programs → the second program's statements are absent,
`success=True, errors=0, warnings=0`. This is why IC228A/IC233A/IC234A/IC235A (6
`PROGRAM-ID`s each) parse "clean" with 3% statement retention. Highest-impact finding:
97% of a file can vanish with a green result.

### C2 — Unknown verbs are silently skipped, even under FAIL_FAST **[verified]**
`parsers/divisions/procedure.py:346-353` and `:483-489`: when
`StatementParserRegistry.find_parser()` returns `None`, the statement is consumed by
`_skip_to_next_statement()` with only a `logger.debug`. Nothing reaches
`ParseResult.errors`/`.warnings`, and FAIL_FAST does not raise.
`core/exceptions.py` defines `UnknownStatementError` — it is **never raised anywhere**.

Real IBM Enterprise verbs with no registered parser, all verified dropped with
`errors=0`: `INVOKE`, `XML PARSE`, `JSON PARSE`, `ALLOCATE`, `FREE`, `EXHIBIT`,
`TRANSFORM`, `SERVICE`, `SEND`/`RECEIVE`, `PURGE`, `ENABLE`/`DISABLE`, `RAISE`,
`RESUME`. At top level, an unknown leading word becomes a **phantom paragraph name**
(`READY TRACE` → paragraph `READY`).

### C3 — `XML GENERATE` / `JSON GENERATE` mis-parse as Report Writer GENERATE **[verified]**
The `XML`/`JSON` keyword is silently consumed (C2 path), then `GENERATE dest FROM src`
matches the Report Writer GENERATE parser and produces a bogus `GenerateStatement`.
The shamrice `json_generate.cbl`/`xml_generate.cbl` examples "parse cleanly" but the AST
is semantically wrong. A wrong node with zero errors is worse than a drop.

### C4 — `GO TO a b c DEPENDING ON x` collapses to `GO TO a` **[verified, open since 2026-07-06 (L5), now known worse]**
`go_parser.py:99-105` reads one target; `_parse_depending_on_clause` returns immediately
when the next token isn't `DEPENDING`. Result: `target_paragraph='P1'`,
`depending_on_variable=None`, leftover `P2 P3 DEPENDING ON X` skipped, and the variable
can become a phantom paragraph. A computed jump table silently becomes an unconditional
branch — control-flow analysis (ProgramFlowAnalyzer, dead-code) is corrupted with
`errors=0`.

### C5 — Level-88 condition names and level-66 RENAMES are lost at the JSON boundary **[verified]**
The parse stage is correct — `ConditionNameItem` / `RenamesItem` nodes exist in the
in-memory AST as children — but **`to_dict()` omits them entirely** (the section
serializer only walks `data_items` of type `CobolDataItem`). Any consumer of
`ast.to_json()` — including the vendored backend per `interface-contract.md` — sees no
88-levels and no RENAMES, with no signal. FD/SD clause metadata (`fd_clauses`: BLOCK
CONTAINS, RECORDING MODE) has the same capture-but-don't-serialize gap.

### C6 — `CALL ... NOT ON EXCEPTION` handler body dropped by `to_dict()` **[verified]**
`models/statements/call.py:104-106` serializes `on_overflow` and `on_exception` but not
`not_on_exception` (the only handler attribute with this gap across all statement
models). Additionally, CALL handler clauses are attached without `add_child`, so
`find_all_by_type()` never sees statements inside them while `get_all_statements()`
does — the two documented traversal APIs disagree (same class as the fixed EVALUATE
defect H1 of 2026-07-06).

### C7 — CLI exit codes: every command exits 0 on a partial/errored parse **[verified/reported]**
`cli/parse.py:340-383`: the only failure path is `ast is None`. Default recovery is
`collect-all`, so a broken program yields a non-None AST + populated `errors` → exit 0.
`--errors` only adds JSON keys. `cobol-parser batch` exits 0 even if **every** file
failed. Any CI/scripting integration gating on exit code treats wrong parses as success.
`ParseResult.success` is computed but never consulted by the CLI.

### C8 — A non-OSError worker exception aborts an entire batch **[reported, code-confirmed]**
`batch.py:82-85,127-130` catch only `OSError`. A `ValueError` from
`normalize_fixed_format` (one bad literal) or `UnicodeDecodeError` (under
`errors="strict"`), or a `BrokenProcessPool`, propagates out of `pool.map` and kills the
whole run — all completed results for the batch are lost. For the advertised
"500–5,000 file" production path, one poisoned file destroys the batch.

## HIGH — silent fidelity loss on common IBM constructs

- **H1 — `ON SIZE ERROR` / `NOT ON SIZE ERROR` bodies keep only DISPLAY and MOVE**
  **[verified; open since 2026-07-06 M1]**. `_utils.py:863-969` skips every other verb:
  `ON SIZE ERROR PERFORM ERR-PARA` → the handler vanishes entirely (not even an empty
  clause), `errors=0`. Affects ADD/SUBTRACT/MULTIPLY/DIVIDE/COMPUTE.
- **H2 — `PERFORM VARYING ... AFTER ...` second dimension lost/garbled** **[verified]**.
  `perform_parser.py` has no AFTER handling; the whole AFTER phrase is absorbed into the
  first UNTIL condition string (with token-type names leaking into it). 2-D table loops
  are silently flattened.
- **H3 — `WRITE ... ADVANCING n LINES/PAGE` drops the count and unit** **[verified]**.
  `write_parser.py:84-106` consumes but never stores them; the model's
  `set_advancing_clause` is never called (`advancing_clause=None`).
- **H4 — `DECIMAL-POINT IS COMMA` is parsed but not honored** **[verified]**. The
  SPECIAL-NAMES clause lands in metadata, but lexing has already treated `,` as a
  separator: `COMPUTE X = 3,14 * 2` → expression `"3 , 14 * 2"`; `VALUE 3,14` is dropped.
  Zero errors. European-formatted programs silently misparse.
- **H5 — SELECT clause drops: `ALTERNATE RECORD KEY`, `PADDING`, `RESERVE`, `SHARING`,
  `LOCK MODE`, second `FILE STATUS` variable** **[reported, code-confirmed]**
  (`environment.py:489-491` `else: consume()`). Secondary-index definitions vanish from
  the AST; `assign_device` is never populated.
- **H6 — Copybook pipeline silent channels** **[reported, code-confirmed]**:
  (a) a `COPY` without a terminating period (or `COPY FOO BAR.`) is never expanded and
  never reported — the copybook's data items simply don't exist;
  (b) `parse_cobol_with_expansion` **discards all expansion warnings** (including lossy
  encoding U+FFFD diagnostics) because it returns only the inner `ParseResult`;
  (c) unterminated `==pseudo-text==` REPLACING operands silently abort the clause.
- **H7 — Unknown `>>IF` condition silently discards the guarded block** **[reported]**
  (`preprocess/__init__.py:612-615` "default to skipping"). Opt-in feature
  (`process_conditionals=True` / CLI `--define`), but when enabled, any condition other
  than `sym IS [NOT] DEFINED` deletes source lines with no signal. Unbalanced `>>IF` /
  stray `>>END-IF` / malformed `>>DEFINE` are also silent; unknown `>>` directives leak
  through as tokens.

## MEDIUM

- **M1 — Unterminated string literals are silent in the default parse path**
  **[verified]**. The pipeline lexes with `free_form=True`, which deliberately suppresses
  the unterminated-string error (`lexer.py:1121`); the 2026-07-06 H5 (hard abort) no
  longer reproduces, but the failure mode is now silence instead of a crash.
- **M2 — Debug lines (`D` in column 7) diverge** **[verified]**: normalizer/lexer emit
  them as *active* code; the copybook path *blanks* them. Same input, two behaviors,
  neither configurable, no signal. (2026-07-06 M3 still open.)
- **M3 — Inline `*>` comments are lexed as code** (`MULTIPLY_OP`+`GREATER`+identifiers).
- **M4 — Continued alphanumeric literals lose trailing blanks** — `rstrip()` on the
  opening line (`preprocess/__init__.py:527`, mirrored in the Cython path) strips blanks
  that are part of the literal per fixed-format rules.
- **M5 — `MemoryConfiguration.max_memory_mb` / `enable_streaming` / `chunk_size_kb` are
  no-ops** — validated, stored, documented, never read. `MemoryLimitExceededError` is
  never raised. Callers who "bounded" memory haven't. `ParseStatistics.memory_peak_mb`
  is always 0.0 in `--stats` output.
- **M6 — `MoveTypeChecker` silently skips every unresolvable MOVE** (UNKNOWN category →
  `continue`, no "skipped" count). A copybook-heavy program yields "0 violations" as a
  false all-clear. Same pattern risk across category-keyed analyzers. It also traverses
  only `children`, so MOVEs inside CALL handlers (C6) are never checked.
- **M7 — `try_parse_nested_statement` swallows all exceptions** (`_utils.py:549-587`).
  Mostly mitigated because parsers pre-record via `report_or_raise`, but nested parsers
  that raise plain `ValueError`/`TokenMismatch` (e.g. `entry_parser.py`) lose the error.
  `except ParseError: pass` in `perform_parser.py:353,397,417` discards VARYING/UNTIL
  diagnostics.
- **M8 — `interface-contract.md` mismatch**: it states `ast` is None when `success` is
  False; under COLLECT_ALL `ast` is non-None with errors. A backend trusting the contract
  discards usable partial ASTs (or, inverted, trusts partial ASTs it shouldn't).
- **M9 — EVALUATE `ALSO` pairing flattened** (subjects/objects kept but not paired);
  COMPUTE/UNTIL/IF-fallback conditions stored as strings, not trees (2026-07-06 M4 still
  open) — structural analysis of arithmetic/conditions impossible.
- **M10 — `coverage.py status` crashes on malformed artifact JSON** (no try/except,
  unlike `cmd_render`).

## LOW

- `&` outside literals silently consumed with no token; unknown column-7 indicator chars
  treated as code; sub-7-char lines dropped (correct per spec, but unsignalled).
- Typed literals (`X'..'`, `N'..'`, `G'..'`) keep raw inner text, no hex validation.
- Comment line interrupting an open continued literal silently severs it.
- Copybook cache hits bypass `total_bytes` accounting → `max_total_size` under-counted.
- `IOWriteStatement.advancing_mode` stored but never serialized (vestigial);
  `value_tracker.get_possible_values` returns `[]` ambiguously for untracked variables.
- Nested `ProfilerContext` over-reports inner peak memory.

## What is genuinely solid (credits)

- **Crash-free and fast**: 0 crashes across 537 files; error recovery around malformed
  statements retains subsequent statements and reports the error; missing periods
  tolerated; recovery cannot swallow a whole following paragraph.
- **Mainstream statement fidelity**: MOVE/ADD/IF/EVALUATE/PERFORM (single-dim)/CALL
  passing modes + ON EXCEPTION bodies/INSPECT combined TALLYING+REPLACING/READ INVALID
  KEY/STRING-UNSTRING clauses all captured; NIST aggregate retention ~100%.
- **DATA DIVISION parse stage is strong**: COMP-1/2/3/5, POINTER, NATIONAL, REDEFINES,
  OCCURS DEPENDING ON + INDEXED BY + KEY, SIGN, SYNC, JUSTIFIED, 88/66 (in-memory), FD/SD
  clauses (as metadata).
- **DECLARATIVES / USE / FILE STATUS / SELECT-ASSIGN** parse correctly.
- **EXEC SQL/CICS/IMS text preserved** including host variables; missing `END-EXEC` now
  reports an error.
- **Copybook structural failures raise properly**: missing copybook (with fuzzy
  suggestions), circular refs, nesting depth, size limits, path traversal.
- **Fixed-format normalization**: string continuation across lines verified correct;
  Cython fast paths verified in **parity** with pure Python (they share the same two bugs
  — M4, M2 — rather than diverging).
- **Tests**: 6,606 pass, 93.4% coverage, regression tests pin the previously fixed
  swallow class.

## Prioritized remediation (smallest set of changes to "production-ready")

1. **Close the unknown-statement hole (C2/C3)** — raise/record `UnknownStatementError`
   (the class already exists) when `find_parser()` returns None; honor FAIL_FAST. This
   single change converts the entire silent class — INVOKE, XML/JSON verbs, EXHIBIT,
   phantom paragraphs — into visible diagnostics, and would also have exposed C1 and C4.
2. **Parse (or at least error on) multi-program units (C1)** — recognize
   `IDENTIFICATION DIVISION` / `END PROGRAM` after the first program; even "unsupported:
   N additional programs found" as an error would eliminate the worst silent loss.
3. **Fix `to_dict()` fidelity (C5/C6)** — serialize 88/66/FD metadata and
   `not_on_exception`; register CALL handler statements as children so the two traversal
   APIs agree. This is the boundary the vendored backend consumes.
4. **Make the CLI and batch honest (C7/C8)** — non-zero exit when `success` is False or
   any batch entry failed; broaden worker excepts to `Exception` → per-file
   `BatchResult.read_error`.
5. **Fix GO TO DEPENDING (C4)** and the clause drops (H1/H2/H3/H5) — or, cheaper interim:
   emit a warning whenever a recognized construct is partially discarded.
6. **Wire the warnings channel** — `parse_cobol_with_expansion` must propagate expansion
   warnings; unknown `>>IF` conditions and un-expanded COPY statements must warn (H6/H7).
7. Decide `D`-line and `DECIMAL-POINT IS COMMA` semantics (M2/H4); document or remove the
   `MemoryConfiguration` no-op fields (M5); align `interface-contract.md` with actual
   `success` semantics (M8).

The unifying theme is unchanged from yesterday's audit but sharper: **the parser has
exactly one working signal channel (errors) and it is only used for what the parser
attempts and fails — never for what it declines to attempt.** Items 1–4 are small,
mechanical changes; with them done, "0 errors, 0 warnings" would actually mean "complete,
faithful AST", which is the bar for production use on real-world IBM COBOL.

## Remediation implemented (same day, this branch)

Findings **C1–C8, H3, and H6(b)** were fixed on this branch after the audit;
pinned by `tests/regression/test_tier3_silent_drop_fixes.py` (30 tests) and
documented in `CHANGELOG.md` (Unreleased) and the OKF bundle:

| Finding | Fix |
|---|---|
| C1 | Multi-program units parsed into `ast.contained_programs` + warning. NIST IC228A: 5 → 171 statements; IC235A: 10 → 293; `subprogram_demo.cbl`: 27 → 53. |
| C2 | Unknown verbs and unparsed clause leftovers now emit `ParseResult.warnings` (two-tier wording). Corpus sweep: 0 → ~1,800 warnings, each marking previously silent content loss (single-digit per realistic program). |
| C3 | New `XmlJsonStatementParser` + `XmlJsonStatement` node for XML/JSON GENERATE/PARSE. |
| C4 | `GO TO ... DEPENDING ON` keeps all targets + variable (peek-ahead, so a missing sentence period cannot eat the next paragraph). |
| C5 | `condition_names` (88) and `renames_items` (66) serialized in `to_dict()`. |
| C6 | `not_on_exception` serialized; CALL handler statements registered as children — traversal APIs now agree. |
| C7 | CLI `parse` exits 2 on an errored parse; `batch` exits 2 when any file failed; analyzers warn on stderr for partial ASTs. |
| C8 | Batch workers contain parse exceptions (and strict-decode failures) as per-file `read_error`. |
| H3 | `WRITE ... ADVANCING n LINES/PAGE` populates `advancing_clause`. |
| H6b | `parse_cobol_with_expansion` propagates expansion warnings. |

Verification after the fixes: full suite green (6,63x passed), corpus re-sweep
unchanged on clean/error counts (455/459 NIST, 24/24 shamrice, 50/54 samples,
0 crashes), total AST statements across the corpus rose from 172,453 to
173,405 with zero new errors.

Still open (tracked, not in this change): H1 (`ON SIZE ERROR` non-trivial
bodies), H2 (`PERFORM VARYING ... AFTER`), H4 (`DECIMAL-POINT IS COMMA`
lexing), H5 (SELECT clause drops), H6a/c (COPY-without-period, REPLACING
pseudo-text aborts), H7 (`>>IF` unknown conditions), and the MEDIUM/LOW
items above.
