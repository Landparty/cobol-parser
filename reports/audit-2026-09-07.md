# cobolparser — repo audit, 2026-09-07

Audit of `main` at `d116e98`. Method was empirical wherever a claim could be
tested: differential harnesses over the sample and NIST corpora, round-trip
property checks against the encoder/decoder's own stated invariants, and
minimal reproductions for every finding below. Findings that could not be
reproduced from a standalone program are not listed.

Every reproduction in this report is a complete program; each was run against
this commit and the output quoted is what it actually printed.

> **Status: all findings below are fixed**, in the same branch as this report
> (`fix: address every finding from the 2026-09-07 repo audit`). Regressions
> are in `tests/regression/test_audit_2026_09_07.py` (18 tests) and the design
> reasoning is in `.okf/log.md`'s 2026-09-07 entry. Two entries changed status
> during the fix pass rather than being fixed: the missing-period diagnostic
> under LOW was **withdrawn** (the parser was right, the audit harness was
> wrong), and M3's coverage half turned out to need a second CI job rather

## HIGH

### H1 — A comparison operand that is not a literal is silently used as one

`cobolparser/analysis/constraints.py:866` (`_build_relational_constraint`).

The function resolves both operands through `ProgramLayoutIndex`. When *both*
resolve it correctly refuses the comparison:

```python
if left_field is not None and right_field is not None:
    unsupported.append(f"{origin}: comparison between two resolved fields not supported in v1: ...")
    return None
```

But when the right operand is a data item the index *cannot* resolve — a
subscripted table element, or any name the index does not carry — it falls
through to the `left_field is not None` branch and the operand's **raw source
text becomes the constraint's value**:

```python
return FieldConstraint(field_ref, op, (_strip_quotes(value_text),), origin, negated=False)
```

Reproduction:

```cobol
       IDENTIFICATION DIVISION.
       PROGRAM-ID. RHS.
       DATA DIVISION.
       WORKING-STORAGE SECTION.
       01  WS-IN     PIC 9(4).
       01  WS-LIMIT  PIC 9(4) VALUE 100.
       01  WS-TAB.
           05 WS-E OCCURS 3 TIMES PIC 9(4).
       01  IDX       PIC 9(1) VALUE 1.
       PROCEDURE DIVISION.
       MAIN.
           ACCEPT WS-IN
           IF WS-IN = WS-LIMIT
               DISPLAY "A"
           END-IF
           IF WS-IN = WS-E (IDX)
               DISPLAY "B"
           END-IF
           STOP RUN.
```

```
resolve('WS-LIMIT')     -> True
resolve('WS-E (IDX)')   -> False
  arm=THEN   field=WS-IN  op=eq  values=('WS-E ( IDX )',)
  arm=ELSE   field=WS-IN  op=ne  values=('WS-E ( IDX )',)
```

`WS-IN` is `PIC 9(4)`. The constraint now claims it must equal the *string*
`WS-E ( IDX )`. Three consequences, in increasing order of severity:

1. Nothing lands in `unsupported` — the gap is invisible where the
   `WS-LIMIT` comparison's identical gap is correctly reported.
2. `ScenarioCoverage` counts both arms **targeted**:

   ```
   "total_arms": 4, "targeted": 2, "merged": 0, "missed": 2
     MAIN@13:5/THEN  missed    "comparison between two resolved fields not supported in v1: WS-IN vs WS-LIMIT"
     MAIN@16:5/THEN  targeted  reason=null
     MAIN@16:5/ELSE  targeted  reason=null
   ```

   The two arms nothing actually targets are the two reported as covered.
3. The `ELSE` scenario is stamped **`verified`**. Its constraint is
   `WS-IN ne 'WS-E ( IDX )'`; the generated value is `4999`; `"4999" !=
   "WS-E ( IDX )"` is true, so `verification.py` returns `satisfied`. The
   self-verification pass cannot catch this because it re-checks the same
   fabricated constraint — it is downstream of the defect, not independent
   of it. (The `THEN` scenario does come back `violated`, so half the damage
   is visible.)

Observed in the wild on `examples/cobol/shamrice/search.cbl`, where
`when ws-item-id-1(idx) = ws-accept-id-1` produces
`ws-accept-id-1 eq 'ws-item-id-1 ( idx )'` across three scenarios.

**Suggested fix.** Require `value_text` to be literal-shaped (numeric literal,
quoted literal, or figurative constant — the figurative case is already
detected just above) before building the constraint. Anything else appends to
`unsupported` and returns `None`, which routes the arm to `missed` with a
reason exactly as the two-resolved-fields case already does.

### H2 — `domains.solve()` returns a witness for constraints it does not model

`cobolparser/analysis/domains.py:342` (`_apply_text`). The tail of the
function is:

```python
    # class_numeric/class_alphabetic and relational ops on text: not
    # meaningfully enforceable on a bare allow/deny set in v1 -- no-op.
    return True
```

`True` means "domain still satisfiable", so `solve()` proceeds to
`domain.pick()` and returns a `Witness`. The constraint is not merely
unmodelled — it is reported as *satisfied*.

Reproduction:

```cobol
       01  WS-TXT  PIC X(10).
       ...
           ACCEPT WS-TXT
           IF WS-TXT IS NUMERIC
               DISPLAY "N"
           ELSE
               DISPLAY "A"
           END-IF
```

```
arm=THEN  op=class_numeric  negated=False  category=alphanumeric  -> solve: 'XXXXXXXX'
arm=ELSE  op=class_numeric  negated=True   category=alphanumeric  -> solve: 'XXXXXXXX'
```

Both arms get the *same* witness, for a field whose value is the only thing
distinguishing them, and the `THEN` witness provably fails its own condition.
The same `return True` covers `lt`/`le`/`gt`/`ge` on text, which is the more
common case.

Confirmed end-to-end on `examples/cobol/shamrice/is_numeric.cbl` and
`mouse_example.cbl`, where `verification` reports `violated` on
`ws-user-input`, `ws-user-input-justified` and `ws-kb-input`.

This is the same family as the already-open A-design note about
`_apply_enum` ignoring relational ops, but the text-domain relational case is
not currently tracked.

**Suggested fix.** Two separable pieces. `class_numeric` on a text field is
genuinely satisfiable — restrict the domain to digit strings and pick one.
Relational ops on text and `class_alphabetic` should return `False` so
`solve()` yields `Unsatisfiable`, putting the arm in `missed` with a reason
rather than handing out a witness that does not satisfy anything.

## MEDIUM

### M1 — `unused-variables` false positives (four kinds)

`UnusedVariableAnalyzer` backs both the `unused-variables` subcommand and the
`unused-variables` lint rule, so each of these is user-visible lint noise on
correct code. Reproductions and actual output:

| Construct | Reported unused | Correct |
|---|---|---|
| `UNSTRING WS-SRC DELIMITED BY WS-DELIM INTO ...` | `WS-DELIM` | used |
| `STRING WS-A DELIMITED BY WS-D INTO WS-OUT` | `WS-D` | used |
| `CALL 'SUB' USING WS-GRP` (group with child `WS-CHILD`) | `WS-CHILD` | used — the whole group is passed by reference |
| REPORT SECTION `05 COLUMN 10 PIC ... SOURCE IN-AMOUNT` | `IN-AMOUNT` | used |

Notes on the last two. Child → parent propagation already works (`MOVE 'X' TO
WS-CHILD` correctly marks nothing unused); it is parent → child that is
missing, which is the direction `CALL ... USING <group>` needs. And the
REPORT SECTION case is new exposure: `SOURCE` / `SUM` / `CONTROL` clauses
became parseable in `data_report_description.py` (PR #196) but the analyzer
still only scans PROCEDURE DIVISION for references, so every Report Writer
program now reports its report fields as dead.

Observed in the corpus on `examples/cobol/shamrice/unstring.cbl`
(`WS-DELIMITER`) and `tests/samples/report_writer.cbl` (`IN-AMOUNT`).

### M2 — `ConstraintReport.unsupported` is empty while real gaps exist

Documented in `CLAUDE.md` and the module docstring as "program-level gaps
(never silently dropped)". In the H1 reproduction:

```
branch-level unsupported: ['IF@13: comparison between two resolved fields ...', 'IF@13/ELSE: ...']
report unsupported: []
```

The gaps do reach `ScenarioCoverage.details` via `scenarios.py:449`, so they
are not lost from the pipeline — but a caller using the documented
`creport.unsupported` field, which is the API the public examples show, gets a
clean list for a program with two unmodelled branches. Either roll branch-level
entries up into the report-level list, or document that `unsupported` is
program-scoped only and point callers at `branch.unsupported`.

### M3 — No CI job runs the test suite

`.github/workflows/ci.yml` has three jobs: `lint`, `typecheck`, and `build`.
`build` does:

```yaml
      - run: pip install -e ".[dev,fast]"
      - run: python setup.py build_ext --inplace
```

`dev` includes pytest. Nothing then invokes it. 9,396 tests and a
`--cov-fail-under=90` floor configured in `addopts` never run on any push or
PR — only the 3-file subset in `cibuildwheel`'s `test-command` runs, and only
at release. `CLAUDE.md` states this openly; `.okf/tests.md` did not — it
described a `test` job gated on `if: github.event_name == 'workflow_dispatch'`,
and no such job was ever in `ci.yml`. Full local run takes 103 s with `-n 4`.

Worth noting alongside: the suite is green both with and without the Cython
extensions, and a differential harness found the two paths byte-identical
across 583 files — so the extension is currently correct, but CI builds it and
never exercises it.

**Fixed, and it needed two jobs rather than one.** pytest now runs in `build`
after `build_ext` (so CI exercises the extensions) with `--no-cov`, and a new
`coverage` job installs `COBOLPARSER_SKIP_EXT=1` and enforces the floor.
coverage.py cannot see into a compiled Cython extension, so once `build_ext`
has run the pure-Python bodies those extensions shadow read as unexecuted:
same suite, same commit, **54.32%** with the extensions built and **91.76%**
without. Gating inside `build` would have failed on the build step rather than
on the code.

That nearly became a spurious finding of its own, and the near-miss is worth
recording. Comparing a coverage total taken *without* extensions (a
1,096-test subset, 59.74%) against one taken *with* them (the full suite,
54.33%) looks like a subset out-covering its own superset — arithmetically
impossible, and it reads as data loss in the tooling. It was written up as an
open finding, ruled-out list and all, before the pure-Python full run came
back at 91.76% and showed the two numbers had never been comparable. Check
which build produced a coverage number before reasoning from it.

### M4 — `views.py` and `layout_offsets.py` disagree in two cases both claim to share

`views.py`'s module docstring: *"That matches `.layout_offsets`, which reports
the same numbers for the `data-items` subcommand … so a byte the layout map
calls offset 12 is the byte the decoder reads there."* Two counter-examples.

**(a) A `REDEFINES` entry wider than what it redefines.**

```cobol
       01  R.
           05 A PIC X(4).
           05 A-R REDEFINES A PIC X(8).
           05 B PIC X(2).
```

`data-items` puts `B` at offset 8 (the slot is `max(4, 8)`); `build_record_views`
puts it at 4, because the base view sums only non-redefining fields and never
consults the overlay's footprint. This is not academic: `RecordView.length` is
what `RecordDecoder._next_frame` cuts fixed-length records at, so the whole
file is framed at the wrong stride and every record after the first is
garbage. Standard COBOL forbids a subordinate redefinition from being larger
than what it redefines, but compilers accept it and real copybooks contain it,
and the two modules should not answer differently either way.

**(b) Offsets after an `OCCURS ... DEPENDING ON` table.**

```cobol
       01  R.
           05 N PIC 9(2).
           05 T OCCURS 1 TO 5 TIMES DEPENDING ON N.
               10 TA PIC X(2).
           05 Z PIC X(1).
```

`data-items` reports `byte_offset: null` for `Z` — honest, since the offset is
per-record data. `build_record_views` reports `12` with
`offset_ambiguous=False` and no caveat. `build_record_views` only ever sets
`offset_ambiguous` on *overlays* (`views.py:308-318`); the base view is
constructed with the field defaulted, so the flag that exists precisely for
this cannot fire on the layout most callers read. `decode --list-views` and
`RecordViews.to_dict()` therefore present a maximum-length guess as a fact.

The decoder itself is fine — `decode_record` resolves ODO from each record's
own counters at decode time, and the `DecodedField.offset` it returns is
correct. Only the static view is affected.

## How it was fixed

All of it landed in one pass. Notes on the calls that were not obvious:

- **H1** needed two operand tests, not one. `IF` operands reach the extractor
  with their quotes intact, so a strict whitelist (quoted or numeric) works
  there. `SEARCH WHEN` and `EVALUATE TRUE` selector *text* has already been
  unquoted by the lexer, so the same whitelist rejected every string literal
  in those constructs — caught by an existing test. Those paths get a looser
  structural test instead: parentheses or internal whitespace means a
  subscript or expression, a bare word may still be a literal.
- **H2** split by what is actually true rather than treating both cases the
  same. Class conditions *are* satisfiable on an alphanumeric field (it can
  hold digits), so they are now modelled; ordering ops genuinely are not
  expressible on an allow/deny set, so they return `Unsatisfiable` with a
  reason. One existing test pinned the old behavior and was rewritten — a
  real behavior change: an arm whose constraints cannot be modelled now
  yields a coverage miss instead of a scenario carrying a caveat.
- **M1**'s CALL fix is deliberately narrow — call arguments only. Propagating
  parent → child for *every* group reference would also silence
  `MOVE SPACES TO WS-GRP`, where "no field is individually referenced" is a
  finding worth keeping. Pinned by a test asserting it survives.
- **M4(a)** did not rework `_place` into full slot semantics. That means a
  second tree walk duplicating `flatten_record`'s OCCURS expansion — exactly
  the drift `views.py` exists to prevent — for a construct no conforming
  compiler accepts. `RecordViews.framing_length` plus a caveat fixes the
  user-visible harm (a shredded file) without that risk.
- **No `bundle_version` bump.** No key was added, removed, retyped or given a
  new meaning; `targeted` and `missed` still mean what they meant. What
  changed is that both are now true. Affected programs report fewer targeted
  arms — the corrected number. Written up in `interface-contract.md`.

Verification: 9,414 tests pass with the Cython extensions built (9,396
existing + 18 new regressions); ruff, black and mypy clean; the pure-Python
coverage job reports 91.76% against a 90% floor.
